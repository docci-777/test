# Low-tier Executor Guide

> 本文件是低阶执行细则，不再是任务派发入口。统一入口为 `docs/CHECKLIST.md`。
>
> 用户只需说：**根据 `docs/CHECKLIST.md` 执行。**

## 如何确定要做哪个任务

低阶模型不得要求用户提供 Issue 或 PR 编号。先读取 `docs/CHECKLIST.md`，按其中自动选择算法：

1. 优先选择最高优先级的 `CHANGES_REQUESTED` 项，并在原分支、原 PR 修复明确问题。
2. 若没有修订项，选择最高优先级的 `READY` 项。
3. 目标 Issue、PR、分支均从清单确定。
4. 没有可执行 `L` 项时停止并报告，不自行解锁 `BLOCKED` 项。

## 开始前必须读取

1. `docs/CHECKLIST.md`：确认自动选择出的任务及当前状态。
2. 目标 Issue 全文及评论：这是单任务目标、允许范围、禁止范围和验收标准的唯一契约。
3. `AGENTS.md` 与 `CONTRIBUTING.md`。
4. 按领域补充读取：
   - 规则任务：`docs/GAME_RULES.md`
   - 架构、公共接口或依赖方向：`docs/ARCHITECTURE.md` 与相关 ADR
   - 产品范围判断：`docs/PRODUCT.md`

若上述信息冲突或不完整，不得自行猜测，立即停止并在 Issue 报告。

## 允许开始的状态

- `READY`：可以首次开始。
- `IN_PROGRESS`：仅该任务原执行者可以继续。
- `CHANGES_REQUESTED`：仅原执行者在原分支、原 PR 修复审查意见。

其他状态一律不得编码。

## 标准执行流程

1. `READY` 任务从最新 `main` 创建清单指定的独立分支；修订任务继续使用原分支。
2. 一个 Issue 只使用一个执行者、一个分支和一个 PR。
3. 只修改 Issue 明确允许或为完成验收必不可少的文件；不得顺手重构、升级依赖、格式化无关文件或扩大功能。
4. 不得改变规则口径、公共接口、核心状态结构或依赖方向；确需改变时先停下并提出高阶决策请求。
5. 实现正常、非法和边界测试；Bug 修复先补回归测试。
6. 禁止通过删除、跳过、弱化测试来让 CI 变绿。
7. 随机场景使用固定 seed；领域代码不得依赖 `Math.random()` 或隐式系统时间。
8. 状态更新必须原子且不可变；失败不得留下部分修改。
9. 提交前运行 `npm run check`。若当前 `main` 尚无该脚本，运行仓库现有全部质量检查并如实记录。
10. 使用 PR 模板创建关联目标 Issue 的唯一 PR，填完整验收证据和实际命令结果。
11. PR 创建后停止扩展功能，等待 CI 与高阶审查。

## 必须停止的情况

出现任一情况立即停止编码，并在 Issue 提问：

- 状态不是允许执行的状态。
- Issue 与规则、架构、产品范围或协作文档冲突。
- 需要修改禁止范围或新增未经批准的依赖。
- 规则、错误码、边界行为、公共接口或依赖方向不明确。
- 发现另一个执行者正在修改同一基础文件或任务分支。
- 为通过验收必须做 Issue 未授权的架构决策。

## PR 交付要求

PR 必须明确包含：实现内容、明确未实现内容、修改文件、每条验收标准的代码/测试证据、实际运行命令与结果、风险/假设/后续事项。

CI 通过不等于允许合并。执行模型不得自行合并，也不得直接向 `main` 推送；低阶模型也不得直接修改 `docs/CHECKLIST.md` 的动态状态。

## 收到审查意见后

- 只修复明确指出的问题。
- 使用原分支、原 PR，不创建第二个 PR。
- 不借审查修复扩大范围。
- 每次推送后等待当前 head 的 CI 和重新审查；旧 head 的“通过”结论自动失效。
