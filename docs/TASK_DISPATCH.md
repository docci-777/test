## 每次派发必须附带的统一约束

1. 从最新 `main` 创建 Issue 专属分支；禁止直接推送 `main`。
2. 先阅读完整 Issue 及其评论，再阅读相关规则与架构文档。
3. 严格遵守“允许修改 / 禁止修改”；不顺手重构、不升级依赖、不扩大功能。
4. 正常、非法、边界场景都要有测试；随机场景必须固定 seed。
5. 禁止领域代码使用 `Math.random()`、系统时钟、网络、UI 或隐式 I/O。
6. 命令失败不得产生部分状态更新；输入状态不得被原地修改。
7. 提交前运行 `npm run check`；若脚本尚不存在，则按当前 `main` 的可用检查执行并如实报告。
8. PR 必须关联 Issue，列出实现/未实现内容、修改文件、验收标准映射、实际命令结果、风险与假设。
9. CI 通过不等于可以合并；必须等待高阶模型审查结论。
10. 不确定规则、公共接口或依赖方向时停止并提问，禁止凭经验补全。

## 高阶模型审查清单

- [ ] PR 只解决一个 Issue，分支与 `Closes #N` 正确。
- [ ] 改动未超出允许文件范围，未夹带依赖升级或无关重构。
- [ ] 每条验收标准都有代码或测试证据。
- [ ] 正常、非法、边界场景完整，测试不是只验证实现细节。
- [ ] 领域层保持纯函数、确定性、不可变更新和正确依赖方向。
- [ ] 错误使用稳定机器可读 code，失败路径无部分状态。
- [ ] CI 的必要检查全部成功，且无未解决审查线程。
- [ ] 审查结论记录为“通过 / 需修改 / 阻塞”，不以口头“看起来可以”代替。
- [ ] 仅在通过后 squash merge，并删除已合并分支。

## 进度更新规则

- Issue 开始：将状态改为“进行中”，记录负责人和 PR 链接。
- PR 需修改：保留原任务，不向另一模型重复派发。
- PR 合并：勾选对应任务，再按依赖表解锁下一波次。
- Issue 关闭但未实施：标记“暂缓/不计划”，不得勾选为已完成。
- 每次 `main` 状态变化后更新本文件，避免派发依据过期。
