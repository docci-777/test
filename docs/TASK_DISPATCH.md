## 你只需要使用的两句话

派发给低阶执行模型：

> 阅读 `docs/TASK_DISPATCH.md` 的“执行模型协议”，按其中当前状态和 Issue #N 完成任务；如果 Issue 不是 `READY` 或 `IN_PROGRESS`，立即停止并报告。

派发给高阶审查模型：

> 阅读 `docs/TASK_DISPATCH.md` 的“高阶模型审查协议”，开始审查 PR #N；把结构化结论记录到 PR，不要自动合并。

这两句话已经要求模型继续读取 Issue、规则、架构、贡献规范和 PR 模板，因此无需在每次派发时重复粘贴全部约束。

## 状态词典

| 状态 | 含义 | 是否可派发 |
| --- | --- | --- |
| `BLOCKED` | 依赖或决策未完成 | 否 |
| `READY` | Issue 契约完整、依赖已合并 | 是 |
| `IN_PROGRESS` | 已指定唯一执行模型与分支 | 仅原负责人继续 |
| `IN_REVIEW` | PR 已创建，等待 CI / 高阶审查 | 否 |
| `CHANGES_REQUESTED` | 原 PR 需要修订 | 仅原负责人继续 |
| `APPROVED` | CI 和高阶审查通过，等待合并 | 否 |
| `DONE` | PR 已合并且 Issue 已完成 | 否 |
| `DEFERRED` | 明确暂缓或不计划，不等于完成 | 否 |

## 执行模型协议

执行模型收到 Issue 编号后，必须按以下顺序工作：

1. 打开本文件，确认目标 Issue 状态为 `READY` 或已由自己负责的 `IN_PROGRESS`；否则停止。
2. 阅读目标 Issue 全文及评论、`AGENTS.md`、`CONTRIBUTING.md`。
3. 按任务领域继续阅读：规则任务读 `GAME_RULES.md`；架构/公共接口任务读 `ARCHITECTURE.md` 和相关 ADR；范围判断读 `PRODUCT.md`。
4. 从最新 `main` 创建本表指定的独立分支。一个 Issue 只能有一个负责人、一个实现分支和一个 PR。
5. 只修改 Issue“允许修改”的文件；禁止修改规则口径、公共接口、依赖方向、本协作控制中心或无关文件。
6. 实现正常、非法和边界测试；随机场景固定 seed；禁止删除、跳过或弱化已有测试。
7. 运行 `npm run check`。若当前 `main` 尚无该脚本，只运行仓库当前已有的质量检查，并在 PR 如实记录。
8. 按 PR 模板创建 PR，使用 `Closes #N`，列出验收标准与代码/测试证据。
9. PR 创建后停止扩展功能，等待 CI 和高阶审查；修订只处理明确意见，不创建第二个 PR。

### 执行模型停止条件

出现以下任一情况必须停止编码并在 Issue 提问：

- 状态不是 `READY` / 本人负责的 `IN_PROGRESS`。
- Issue 与规则、架构或本文件冲突。
- 需要修改禁止范围、引入新依赖或改变公共接口。
- 规则、错误码、边界行为或依赖方向不明确。
- 发现另一个模型正在修改同一基础文件或分支。

### 执行模型交付格式

PR 必须包含：实现内容、明确未实现内容、修改文件、验收标准逐项证据、实际命令与结果、风险/假设/后续事项。CI 通过不等于可以合并。

## 高阶模型审查协议

高阶模型收到 PR 编号后，必须按以下顺序审查：

1. 读取本文件，确认 PR 对应任务、依赖与预期状态。
2. 阅读目标 Issue 全文及评论，并读取 `AGENTS.md`、相关规则/架构/ADR。
3. 固定记录 PR head SHA，读取完整 diff、变更文件、提交、CI、评论、reviews 和未解决线程。
4. 逐条验证 Issue 验收标准；不要只相信 PR 描述中的“已通过”。
5. 检查范围是否越界、依赖是否获批、领域层是否纯函数且确定、失败是否原子、状态是否不可变、隐藏信息是否安全。
6. 检查正常/非法/边界测试是否覆盖真实行为，是否存在概率断言、弱化测试或只测实现细节。
7. 先写 findings，按 `阻塞 > 重要 > 建议` 排序，并给出文件/位置、证据、影响和最小修复要求。
8. 给出唯一结论：`通过`、`需修改` 或 `阻塞`；把结构化结论记录到 PR。
9. 除非仓库所有者明确要求，高阶模型不得自动合并。head 变化后原审查失效，必须审查增量并更新结论。

### 审查输出模板

```markdown
审查 head：<SHA>
结论：通过 / 需修改 / 阻塞

## Findings
1. [阻塞/重要/建议] <问题>
   - 证据：<文件、位置、CI 或复现>
   - 影响：<为什么重要>
   - 最小修复：<限定范围的修复要求>

## 验收核对
- [x/ ] <Issue 验收项与证据>

## 门禁
- CI：通过 / 失败 / 未完成
- 未解决线程：0 / N
- 范围：合规 / 越界
- 合并建议：可合并 / 修订后复审 / 不得合并
```

若审查身份与 PR 作者相同，GitHub 可能不能形成正式 Approval；仍需以 `COMMENTED` 或 PR 评论留下上述结构化结论，并明确它不是独立账号批准。

## 生命周期与文档更新

| 事件 | 本文件更新 | 责任人 |
| --- | --- | --- |
| 准备派发 | 核验依赖后将任务改为 `READY` | 高阶模型 |
| 已派发 | 改为 `IN_PROGRESS`，填写负责人、分支 | 高阶模型 |
| PR 创建 | 改为 `IN_REVIEW`，填写 PR 和 head | 高阶模型 |
| 审查需修改 | 改为 `CHANGES_REQUESTED`，保留原负责人 | 高阶模型 |
| 审查通过 | 改为 `APPROVED`，记录已审查 head | 高阶模型 |
| PR 合并 | 改为 `DONE`，更新下游依赖并刷新 README/ROADMAP 的里程碑摘要 | 高阶模型 |
| 暂缓/取消 | 改为 `DEFERRED` 并写明原因，不勾选完成 | 所有者 / 高阶模型 |

更新规则：

- 低阶执行模型不得为了“顺便同步进度”修改本文件；状态由高阶模型在 GitHub 实际状态变化后维护。
- 不在 README、ROADMAP、Issue 和本文件重复保存同一份逐任务状态。
- README 只展示项目入口和一句当前阶段摘要；ROADMAP 只展示里程碑。
- 新增 Issue 前必须先写完整契约；新增文档前先检查职责地图，避免创建功能重叠文件。
- 每次更新本文件时同时更新“最后核对”日期，并重新查询开放 Issue、PR、CI 与审查线程。

## 合并门禁

只有同时满足以下条件才可建议合并：

- Issue 契约完整且依赖已合并。
- 改动未越界，所有验收项有证据。
- 必要 CI 全部成功。
- 没有未解决的阻塞/重要审查意见。
- PR head 与最后审查的 SHA 一致。
- 高阶模型结论为“通过”。

合并方式为 squash merge，并删除已合并任务分支。Issue #10 暂缓期间，仓库所有者需人工遵守这些门禁。
