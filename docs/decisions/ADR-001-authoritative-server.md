# ADR-001 — 权威服务端、命令协议与恢复模型

**Status:** ACCEPTED  
**Date:** 2026-09-03  
**Decision Owners:** 高阶 Planner  
**Related Tasks:** TASK-003, TASK-004, TASK-005, TASK-006, TASK-007, TASK-009, TASK-010  
**Supersedes:** None  
**Superseded By:** None

## Context

本项目需要在不可信的 3–4 个浏览器之间保持唯一游戏事实，并正确处理秘密手牌、随机结果、并发交易、重复请求、断线重连和服务重启。若客户端各自执行规则或以最后写入为准，局域网延迟和刷新就可能产生分叉、双花或秘密泄露。

## Decision

采用单进程权威服务端和每房间串行命令模型：

1. 浏览器只发送带 commandId 与 expectedRevision 的玩家意图。
2. 服务端用纯领域引擎验证并原子应用命令，生成单调 revision 和领域事件。
3. 对每个连接发送“公开视图 + 该玩家私有视图”，不广播完整 GameState。
4. commandId 结果在玩家范围幂等；旧 revision 明确拒绝并返回追平指示。
5. 首次入座签发高熵重连令牌，服务端仅保存校验摘要；断线不移除座位或自动行动。
6. 成功状态变更写入带 schemaVersion/rulesetVersion 的本地原子快照，服务重启恢复未结束房间。
7. 随机数、时钟、ID 和存储均通过端口注入领域/应用层，测试使用确定实现。

## Rationale

- 所有规则和随机结果只有一个裁判，最容易保证公平与一致性。
- 视图投影把“可以同步状态”和“可以看到秘密”分开。
- revision + commandId 同时处理乱序与重复，比依赖 Socket 恰好一次交付可靠。
- 每房间串行化符合回合制负载，无需分布式锁。
- 本地快照满足局域网零外部依赖，并给未来迁移数据库留下适配器边界。

## Alternatives Considered

### Option A — 浏览器点对点/房主客户端裁决

- 优点：可减少独立服务端逻辑。
- 缺点：秘密隔离、断线、主机刷新和作弊边界复杂，状态容易分叉。
- 未选择原因：与“权威服务端规则引擎”目标冲突。

### Option B — 事件溯源数据库作为首版核心

- 优点：审计和回放天然完整。
- 缺点：引入额外基础设施、迁移和恢复复杂度，超出家庭 LAN MVP。
- 未选择原因：快照 + 精简公开事件日志已满足首版恢复和诊断。

### Option C — 仅内存房间

- 优点：实现最简单。
- 缺点：服务进程重启即丢局，无法满足可恢复目标。
- 未选择原因：接受轻量本地快照的成本以提升实际可玩性。

## Consequences

### Positive

- 非法、重复和并发动作有统一处理路径。
- 私密数据泄露可通过投影合约测试集中审查。
- 网络与 UI 可替换而不改变规则引擎。
- 单机部署仍可恢复未完成游戏。

### Negative / Trade-offs

- 服务端进程是房间可用性的单点。
- 每次状态变化需考虑快照写入时机和失败处理。
- 协议、快照和规则版本必须显式维护。
- 客户端预测只能改善体验，不能绕过服务端等待。

## Validation / Revisit Trigger

出现以下情况时重新评估：

- 要求跨多台服务主机扩展或公网高可用；
- 同时房间量使单进程串行模型成为可测瓶颈；
- 需要完整可验证回放或长期赛事审计；
- 本地快照无法满足数据生命周期或安全要求。
