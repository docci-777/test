# 项目统一执行清单

> **唯一派发口令：`根据 docs/CHECKLIST.md 执行。`**  
> 最后核对：2026-09-02  
> 维护者：仓库所有者或高阶模型  
> 本文件是整个项目协作的唯一动态入口：当前状态、执行顺序、任务选择、审查顺序、解锁条件和里程碑完成情况都从这里开始。

任何模型收到“根据清单执行”后，不需要用户再提供 Issue、PR、分支或下一步编号；这些对象必须由模型根据本清单和 GitHub 当前事实自行确定。

## 1. 所有模型先执行的选择算法

1. **先核对 GitHub，而不是直接相信清单。** 查询开放 Issue、开放 PR、当前 head、CI、reviews、未解决线程和合并状态；GitHub 实际事实优先于本文件中的旧状态。
2. **识别自己的工作角色：**
   - `L`（低阶执行）：实现代码、补测试、处理原 PR 的明确修改要求；不得做架构/规则决策、正式审查或直接修改 `main` 上的协作状态。
   - `H`（高阶规划/审查）：核对状态、完善任务契约、规划依赖、审查 PR、更新本清单和协作文档；默认不替代低阶模型实现功能代码。
   - `O`（仓库所有者门禁）：合并、启用仓库设置等需要所有者明确授权的动作。普通模型遇到 `O` 条目时不得自行越过。
3. **从“当前执行队列”顶部向下扫描，选择第一个：**未完成、前置条件满足、且角色与自己匹配的条目。
4. 不得要求用户补充 Issue/PR 编号；目标对象直接使用该条目记录的 Issue、PR、分支或“自动选择规则”。
5. 完成一个条目后，如果下一条仍属于自己的角色且没有外部阻塞，应继续执行；遇到其他角色门禁、CI 等待、依赖未满足或关键歧义时停止并报告。
6. `L` 模型不得为了更新进度直接修改本文件；其 GitHub 提交/PR 是状态证据。`H` 模型每次工作时应先根据 GitHub 实际状态修正本文件，再继续下一项。

## 2. 自动任务优先级

当表格状态与 GitHub 事实发生变化时，按以下优先级自动选择工作，不需要用户指定对象：

### 低阶模型 `L`

1. 先找最高优先级的 `CHANGES_REQUESTED` 任务，并在**原分支、原 PR**修复明确问题。
2. 如果没有需要修订的任务，选择最高优先级的 `READY` 任务，从最新 `main` 创建清单指定分支并实现。
3. `BLOCKED`、`IN_REVIEW`、`APPROVED`、`DONE`、`DEFERRED` 一律不得开始新编码。
4. 若没有可执行的 `L` 条目，停止并报告“当前无低阶可执行项”，不要自行解锁任务。

### 高阶模型 `H`

1. 先核对并修正本清单与 GitHub 实际状态。
2. 优先审查当前 head 已稳定且 CI 已完成的 `IN_REVIEW` PR；若 head 变化，旧审查自动失效。
3. 对 `CHANGES_REQUESTED` 任务，只核对修改要求是否清楚；不要代替原执行模型修代码。
4. PR 合并后立即更新任务为 `DONE`，重算依赖，并把第一个满足条件的任务改为 `READY`。
5. 没有待审 PR 时，优先完善即将解锁任务的 Issue 契约、解决高阶决策前置或拆分 ROADMAP 中下一批尚未建 Issue 的工作。
6. 不得因为“没有 PR 可审”而实现本应交给 `L` 的功能任务。

### 所有者 `O`

只有在用户明确要求模型代为合并或修改仓库设置时才执行 `O` 项；否则普通模型应停在门禁前并报告。

## 5. 单任务生命周期清单

每一个实现任务都必须按下面的顺序推进。模型只需自动选择当前任务，不需要用户提供编号。

- [ ] `H`：确认依赖已经实际合并、Issue 契约完整，将任务标记为 `READY`。
- [ ] `L`：从最新 `main` 创建清单指定独立分支，实现 Issue，完成正常/非法/边界测试。
- [ ] `L`：运行 `npm run check`（若尚不存在则运行当前全部质量检查），按模板创建唯一 PR。
- [ ] `H`：固定当前 head，核对完整 diff、Issue、CI、reviews、线程和相关规则/架构资料。
- [ ] `H`：先写 findings，再给出唯一结论 `通过 / 需修改 / 阻塞`。
- [ ] `L`：若需修改，只在原分支、原 PR 修复明确意见；新 head 重新走 CI 与复审。
- [ ] `O`：当前 head 通过且 CI 成功后 squash merge。
- [ ] `H`：根据 GitHub 实际合并结果标记 `DONE`，重算下游依赖并更新本清单。

## 6. 任务状态词典

| 状态 | 含义 | 下一角色 |
| --- | --- | --- |
| `BLOCKED` | 依赖或关键决策未完成 | `H` 处理前置或等待 |
| `READY` | 契约完整、依赖已满足 | `L` |
| `IN_PROGRESS` | 唯一执行者正在原分支实现 | `L` |
| `IN_REVIEW` | PR 已创建，等待当前 head 的 CI / 审查 | `H` |
| `CHANGES_REQUESTED` | 当前 PR 有明确需要修复的问题 | 原 `L` |
| `APPROVED` | 当前 head 的 CI + 高阶结构化审查通过 | `O` |
| `DONE` | PR 实际合并、任务完成 | `H` 解锁下游 |
| `DEFERRED` | 明确暂缓，不等于完成 | 无，直到重新启用 |

## 8. 清单更新原则

- 本文件中的动态状态只由仓库所有者或 `H` 模型根据 GitHub 实际事实更新。
- 每次 PR 创建、head 变化、CI 变化、审查结论变化、合并、Issue 关闭/重开、依赖解锁后，都应重新核对本文件。
- checkbox 只有在对应完成判据被 GitHub/CI/代码事实验证后才能勾选。
- 不在 README、STATUS、TASK_DISPATCH 或 ROADMAP 复制逐任务实时状态；这些文件只应链接本清单或保存稳定长期信息。
- 若本清单与 GitHub 实际状态冲突，先按 GitHub 修正清单，再继续执行。
