# High-tier Review Guide

> 本文件是高阶审查细则，不再是审查派发入口。统一入口为 `docs/CHECKLIST.md`。
>
> 用户只需说：**根据 `docs/CHECKLIST.md` 执行。**

## 如何确定要审查哪个 PR

高阶模型不得要求用户提供 PR 编号。先读取 `docs/CHECKLIST.md` 并核对 GitHub：

1. 优先选择最高优先级、当前 head 已稳定且 CI 可核对的 `IN_REVIEW` PR。
2. 若任务是 `CHANGES_REQUESTED`，只核对修改要求是否清楚，不代替低阶模型修代码。
3. 若没有待审 PR，按清单执行合并后解锁、Issue 契约完善或下一批规划工作。
4. 目标 Issue、PR 和相关资料由清单及 GitHub 自动确定。

## 审查前必须读取

1. `docs/CHECKLIST.md`：确认自动选择出的 PR、依赖、当前阶段与完成判据。
2. 目标 Issue 全文及评论。
3. `AGENTS.md`。
4. 按改动领域读取 `docs/GAME_RULES.md`、`docs/ARCHITECTURE.md`、相关 ADR 与 `docs/PRODUCT.md`。
5. 完整 PR：当前 head SHA、diff、变更文件、提交、CI、评论、reviews 和未解决线程。

不得只依据 PR 描述或执行模型自报的测试结果下结论。

## 审查步骤

1. 记录当前 PR head SHA；所有结论只对该 SHA 有效。
2. 核对依赖是否已满足，Issue 是否具备完整契约。
3. 逐条验证 Issue 验收标准，并给出实际代码、测试、CI 或复现证据。
4. 检查是否越出 Issue 允许范围，是否有未批准依赖或架构变化。
5. 检查领域层确定性、纯函数边界、原子失败、输入不可变、隐藏信息安全和依赖方向。
6. 检查正常、非法、边界测试是否验证真实行为；拒绝概率性断言、弱化测试或只测实现细节。
7. 检查 CI 是否针对当前 head 成功，所有阻塞/重要线程是否已解决。
8. 先输出 findings，再给出唯一结论：`通过`、`需修改` 或 `阻塞`。
9. 把结构化结论记录到 PR；除非仓库所有者明确要求，不自动合并。

## Findings 严重度

- `阻塞`：违反契约、规则/架构错误、数据/状态安全风险、验收失败、CI 失败、无法可靠合并。
- `重要`：明显缺陷、边界缺失、测试不足或维护风险，合并前应修复。
- `建议`：非必须改动；不得把偏好性建议包装成阻塞。

每个 finding 都应包含：问题、证据、影响、最小修复要求。优先要求最小范围修复，避免借审查扩大任务。

## 审查输出模板

```markdown
审查 head：<SHA>
结论：通过 / 需修改 / 阻塞

## Findings
1. [阻塞/重要/建议] <问题>
   - 证据：<文件、位置、CI 或复现>
   - 影响：<为什么重要>
   - 最小修复：<限定范围的修复要求>

## 验收核对
- [x/ ] <Issue 验收项与证据>

## 门禁
- CI：通过 / 失败 / 未完成
- 未解决线程：0 / N
- 范围：合规 / 越界
- 合并建议：可合并 / 修订后复审 / 不得合并
```

如果没有 findings，明确写“无阻塞、重要或建议级问题”。

## Head 变化规则

- PR head 一旦变化，旧审查结论自动失效。
- 必须比较“上次已审查 head → 当前 head”的增量，并重新核对当前 head 的 CI、线程与验收证据。
- 只有当前 head 存在结构化“通过”结论且 CI 成功，才能把任务状态改为 `APPROVED`。

## 审查后的清单维护

审查完成后，按 `docs/DOC_MAINTENANCE.md` 更新 `docs/CHECKLIST.md`：

- 有阻塞/重要问题：任务为 `CHANGES_REQUESTED` 或必要时 `BLOCKED`。
- 当前 head 通过且 CI 成功：`APPROVED`。
- 合并后：`DONE`，并重新计算下游任务是否可变为 `READY`。

若审查身份与 PR 作者相同，GitHub 可能不能形成正式 Approval；仍应以 Review Comment 或 PR Conversation 留下完整结构化结论，并注明不是独立账号批准。
